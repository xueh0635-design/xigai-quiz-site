# 架构与可靠性改造

本次改造保留静态 Web + Capacitor + Supabase 的部署方式。目标是让学习数据更可靠，让源码、题库、数据库与发布制品可以核对和重建。业务功能继续按模块逐步整理，不引入新的应用框架或微服务。

## 源码与产物

`web/index.template.html` 保存页面结构，`web/styles/` 保存原有样式，`web/scripts/` 保存按功能拆出的脚本，`content/` 保存结构化内容。`web/scripts.json` 显式规定脚本顺序和数据入口。账号及存储模块由 esbuild 打包。其余脚本保持原来的执行时序，避免这次迁移同时改变页面生命周期。

运行 `npm --prefix mobile run build:web` 会生成整个 `docs/` 目录和资源清单。大幅插画已经从 HTML 的 base64 数据分离为资源文件，CSS 带内容哈希；题库仍直接包含在 HTML 中，使原生离线包无需首次联网下载题目。此阶段没有新增 Service Worker，浏览器版不承诺关闭页面后仍能无网重新加载整个应用。

`web-manifest.json` 记录全部应用资源的 SHA-256，以及题库文件的版本哈希。它不包含自身和发布公告 `android-update.json`。原生打包前逐项校验并复制清单里的文件，避免漏带样式或图片。构建器检查核心 HTML 压缩后不超过 1.2 MB，禁止大型 base64 插画重新进入核心文件。该预算衡量核心文件，不等于首次使用全部功能的网络总流量。

修改来源文件后重建并提交产物。不要直接修改 `docs/index.html`：CI 的逐字节重建校验会拒绝这种漂移。`npm run build:sync` 保留为构建完整 Web 目录的兼容命令。

## 学习数据分层

学习状态区分当前题目快照、每次作答事实、各任务草稿和章节测验成绩。快照负责快速显示当前状态；统计使用作答事件，避免重复作答覆盖之前日期的事实。已上传事件保持不可变，重试用相同的事件 ID 去重。

浏览器持久化使用 IndexedDB 事务，把状态变化和待同步项一并写入。同一账号的不同标签页读取同一个持久队列，避免旧的内存快照覆盖其他标签页尚未上传的数据。游客与各个账号使用不同作用域，切换账号不自动把游客记录归属给登录用户。

上述保证覆盖独立记录和追加事件，不代表同一份未交卷试卷支持多人或多窗口协同编辑。同一草稿仍按记录版本采用最后写入的快照；同时在两台设备编辑同一份试卷，尚未交卷的选择可能被另一份快照替换。需要无损协同编辑时，应另行设计按题目版本合并或编辑冲突提示。

IndexedDB 提高事务一致性，但不保证系统永不清理存储，也不能保证用户强制关闭进程前每次尚未完成的写入都已落盘。原生端独立持久层、用户可下载的学习记录导出和更完整的诊断页面仍是后续工作。

## 题库身份与统计口径

共享题目的归一化规则由 `web/scripts/question-catalog.js` 给页面和内容校验器复用。选项字母重排不应制造新题，答案不同的题不能合并。当前内容有 1,685 个原始条目、1,682 道规范题，其中 1,585 道是可练习的客观题，97 道是阅读题。完成度的分母使用可练习的规范题。

题库版本来自 `content/questions.json` 的原始 UTF-8 字节哈希。修改内容时需要同步生成新的后端题库迁移，保证旧事件仍携带原版本、服务端能按提交版本校验答案。单机内容校验会拒绝重复 ID、错误答案键、断开的题目引用和不对应选项的解析。

原有多人玩法的选题资格保持独立。补齐单人练习判分数据，不会自动把原本不支持多人玩法的题目加入对局；需要单独审阅和迁移才能扩充多人题池。

## 后端与兼容部署

后端目录恢复了线上实际使用但仓库遗漏的迁移和 Edge Functions，并记录迁移编号与恢复范围。固定同桌的数据切换操作单独保存在 operations 中，空库初始化不会创建或猜测真实用户配对。详情以 backend 中的恢复说明和本地数据库测试为准。

新同步协议采用增量游标、精确确认和追加作答事件。服务端根据认证身份确定数据所有者；请求中的账号只用于核对，不能作为授权依据。事件重试必须幂等，分页不能因为并发事务提交顺序而跳过变化。旧 RPC 保留兼容，升级客户端在旧后端下保留尚不能上传的新数据。

部署顺序：先在隔离的 Supabase 环境重放迁移并检查权限、题库版本和云函数配置，再发布兼容后端，验证旧客户端仍能同步，然后发布新 Web 与原生客户端。本 PR 的本地数据库测试不执行生产 SQL，也不部署云函数。历史快照只能作为带明确来源的迁移基线，无法重建过去已经被覆盖的每次作答。

## 发布约束

同一源码提交必须通过内容/单元校验、数据库测试、真实浏览器流程、Android 构建与 iOS 模拟器流程，聚合检查名称为 `release-gate`。CI Android 制品中记录源码 SHA 和 Web 清单摘要。维护者下载该制品进行签名，发布器比对其与 CI 原始 APK 的非签名 ZIP 内容，禁止签名后夹带重新构建的代码。

源码合并与生产数据库迁移、原生应用发布是不同的交付步骤。正式发布需要维护者使用原有签名密钥，按 README 中的流程操作。iPhone 对旧版本的兼容路径仅用于历史无清单制品；有清单却校验失败的版本不能退回旧路径绕过验证。

## 验证与边界

```sh
npm --prefix mobile ci
npm --prefix mobile run build:web
npm --prefix mobile run verify
npm --prefix mobile run test:database
# 浏览器测试另需安装与锁文件版本一致的 Chromium：
cd mobile
npx --no-install playwright install --with-deps chromium
node --test tests/browser/*.cjs
```

PGlite 测试执行 PostgreSQL 迁移与数据库授权路径，并用最小 auth/storage 适配模拟 Supabase 环境。它不能替代一次真实 Supabase staging 验证，尤其是邮件回调、存储策略、Realtime、外部模型供应商与部署配置。Android 和 iOS 的平台构建结果以该提交的 CI 为准。

后续工作的优先级：原生独立持久层与导出恢复、同步/存储诊断、服务端查询负载和统计预聚合、可选功能的按需加载，以及更深入的交互和无障碍回归。每一步应围绕实际故障风险和测量结果推进。
